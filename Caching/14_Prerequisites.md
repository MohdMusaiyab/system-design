# 14. Prerequisites & Foundations Mapping

While reading through this guide, we relied heavily on core computer science foundations. This mapping shows exactly *why* those prerequisites are necessary and *how* we applied them in production caching scenarios.

| Prerequisite Topic | Category | Why We Needed It & How We Applied It |
| :--- | :--- | :--- |
| **Hash Tables (HashMap / Dict)** | Data Structures | The fundamental engine of every cache. We needed O(1) average time complexity for GET and SET. Without hash tables, caches wouldn't exist. We also relied on the concept of collision resolution to understand how Redis/Memcached handle hash collisions internally. |
| **Linked Lists (Doubly)** | Data Structures | Critical for implementing LRU (Least Recently Used) eviction. We move nodes to the head on access and remove from the tail on eviction—both O(1) operations. We needed to understand pointer manipulation to grasp why Redis uses approximated LRU (to avoid the spinlock overhead of moving nodes in a multi-threaded environment). |
| **Heaps / Priority Queues** | Data Structures | While not used in LRU, we encountered LFU and TTL heaps. Redis internally uses a radix tree or skiplist for sorted sets, but conceptually, expiration timers require a priority queue to efficiently find the key with the lowest TTL. |
| **Probabilistic Data Structures** (Bloom Filters / Count-Min Sketch) | Data Structures | Bloom Filters were our defense against Cache Penetration (checking existence of a key in O(1) space). Count-Min Sketches are used internally by TinyLFU (Caffeine) to track frequency of hundreds of millions of keys without using massive memory—trading absolute accuracy for space efficiency. |
| **Time Complexity (Big-O Notation)** | Algorithms | Every single engineering decision in eviction and sharding is a Big-O trade-off. We chose LRU because eviction is O(1). We avoid scanning the entire 10GB Redis dataset (O(N)) and use random sampling instead. We needed to understand the cost of operations to justify our architectural choices. |
| **Hashing Algorithms** (MD5, SHA, CRC16) | Algorithms | Consistent Hashing and Redis Hash Slots rely on deterministic hashing. We needed to understand that a good hash function distributes keys uniformly. `CRC16(key) % 16384` determines which Redis node owns the key. We also relied on hashing for Cache Busting (generating unique version strings). |
| **Memory Hierarchy** (Registers → L1/L2 → RAM → Disk) | OS / Computer Architecture | The absolute foundation of Section 3. We understood why we cache because of the physical latency gap. We needed to know that RAM is volatile and disk is persistent, which directly justifies why we use RDB/AOF for Redis persistence. |
| **Virtual Memory & Paging** | Operating Systems | Essential for understanding the OS Page Cache (Section 3). We realized that the OS caches file blocks independently of our application. We also relied on this to understand `fork()` behavior in Redis—how Redis uses Copy-on-Write (COW) to create RDB snapshots without blocking the main thread. |
| **Kernel vs. User Space / syscalls** | Operating Systems | To understand why Local/In-Process caches are sub-microsecond while Distributed caches take ~1ms. A local cache is a simple pointer dereference in user space. A distributed cache requires a `read()` or `write()` syscall, context switching into kernel space, and traversing the network stack. |
| **Context Switching & Thread Scheduling** | OS / Concurrency | Critical for understanding Cache Stampedes and Connection Pool Exhaustion. If hundreds of threads block waiting for Redis, the OS scheduler swaps them out, causing high CPU context-switch overhead. We needed to know this to justify non-blocking I/O or asynchronous recomputation strategies. |
| **TCP/IP, Sockets, and Network RTT** | Networking | Everything in a Distributed Cache (Redis/Memcached) travels over TCP sockets. We relied on understanding Round-Trip Time (RTT)—typically ~0.5ms–1ms within a datacenter—to explain why distributed caches are slower than local ones. We also needed Network Timeouts and Connection Pools because TCP connections are finite resources. |
| **Network Partitions (Split-Brain)** | Distributed Systems | We discussed this in Section 10. A network partition is a fact of life in distributed systems. We needed the prerequisite concept of asynchronous networks (messages can be delayed, dropped, or reordered) to understand why Redis Sentinel uses a quorum to avoid split-brain. |
| **CAP Theorem** (Consistency, Availability, Partition Tolerance) | Distributed Systems | We used this implicitly in Section 8 (Consistency Models). Caches force a trade-off. Strong Consistency (Write-Through) sacrifices Availability (if Redis is down, writes fail). Eventual Consistency (Cache-Aside) sacrifices Consistency for Availability. We needed CAP to justify why we choose Weak Consistency for catalogs and Strong for financial data. |
| **Leader-Follower Replication** (Async Replication) | Distributed Systems | To understand Redis Replicas (Section 9). We needed to know that replication is asynchronous, meaning the replica lags behind the primary. This directly caused the "Replication Lag" problem we discussed, forcing us to route critical reads to the primary. |
| **Transactions / ACID** (Atomicity, Durability) | Database Fundamentals | Crucial for the Leaky Cache problem and Write-Through patterns. We relied on the concept of Atomicity (all or nothing) to explain why we should never update the cache before the DB transaction commits. We also relied on Durability (via fsync and AOF) to guarantee we don't lose writes. |
| **Serialization & Deserialization** | Computer Science / Software Engineering | We didn't just store raw bytes. We stored complex objects. We needed the prerequisite knowledge of how a struct or class is flattened into bytes (JSON, Protobuf, MsgPack). Without this, we couldn't explain the trade-offs in Section 9 (CPU overhead vs. Memory footprint vs. Network bandwidth). |
| **Mutexes / Locks (Concurrency Control)** | Concurrency / OS | Required for Section 10 (Mitigating the Thundering Herd). We used `SETNX` (Redis lock) to ensure only one thread recomputes a cache value. We needed to understand deadlocks and lock timeouts to prevent the "mutex lock" from becoming a point of failure itself. |
| **Asynchronous Processing / Message Queues** | Software Architecture | Used heavily in Event-Based Invalidation and Write-Behind. We needed to understand that messages can arrive out-of-order, requiring us to implement versioned events. Without this background, the invalidation strategy would feel magical and prone to failure. |
| **Statistical Distributions** (Zipfian / Pareto) | Mathematics / Probability | The backbone of Section 2. We relied on the mathematical understanding that real-world access patterns are not uniform. The 80/20 rule is a Zipfian distribution. We used this to calculate hit ratios and justify why caching the top 20% of keys gives us 80%+ hit rates. |
